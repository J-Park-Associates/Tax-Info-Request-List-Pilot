| P46 | 2026-09-29 | Terms acceptance and "tour seen" are kept in the tracker's own record, `pilot-record.json` in the data folder, through a new API command `pilot-record` on the existing channel. The window's local storage is only a cache. When the cache says nothing, the page asks the record before the terms stay, and it closes the terms (without starting the tour) when the record holds this version. When neither can answer, the terms show, as before. The shell also writes the page's storage to disk as the window closes. This supersedes P9. | The pilot 0.1 Windows check: after a restart the terms and tour came back, though storage held both. The restart's window never opened its storage (its log shows no open, and nothing was written). `main.js` already holds the single-instance lock (line 405), but Electron releases that lock when the app starts quitting, before it closes the page's storage. So a quick restart gets a window whose storage is still locked by the closing app. Chromium then falls back to empty in-memory storage without saying so, which is what the log shows. No change to `main.js` can make that storage reliable. A record the tracker owns can. |
| P47 | 2026-09-29 | Only one after-install run happens at a time. `after_install.run()` and `launch()` hold one lock, `after-install.lock` beside the record, from before the saved schedule choice is read until the record is written. So whichever run acts last acts on the choice saved last. A run that waits 10 minutes without getting the lock changes nothing and says so. A lock left by a process that has ended is taken over (`locking`'s rule). Every task the step removes is noted on the local debug log with why. | The pilot 0.1 Windows check lost the task after Off, then On, then a restart. Replayed in order, those steps keep the task (`test_the_windows_check_sequence_keeps_the_task_through_a_restart`). The only ways the step removes a task are `_off()` and ELSEWHERE, and the designation rules ELSEWHERE out. So the loss needs a run that read "off" and acted after "on" was registered. Every door is its own process: the launch step runs unwaited in the background and outlives its window, and the restart overlap in P46 starts another. Before this, nothing stopped two runs from overlapping. `test_a_run_that_read_off_never_removes_what_a_later_on_registered` reproduces the loss without the lock and passes with it. Which overlap happened on the test PC is not recorded (the PC keeps no Task Scheduler history). The next run's debug log will name any removal. |
