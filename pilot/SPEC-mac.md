# Running Tax Document Console on a Mac: what it would take

Read-only assessment of branch `claude/zealous-faraday-hw5sga` (repo map current: 254 nodes, 2026-10-09). Nothing in the repository was changed. PyPI wheel lists were checked live on 2026-10-10.

## Verdict

The engine is the part that reads, sorts, files and drafts, and it is already portable. It is standard Python, its suite passes on Linux (a close relative of macOS), and every package it reads with publishes Apple Silicon builds. The hash-checked lock already lists those builds. Everything around the engine is Windows-only:

- **Scheduling.** The nightly job is registered with Task Scheduler.
- **The settings file.** It lives beside the program, and a Mac app bundle forbids writing there.
- **Safeguards that are off on a Mac today.** Four of them do nothing on a Mac and say nothing about it:
  - the refusal to run from a removable drive;
  - the memory cap on a reading;
  - the rule that a held lock cannot be deleted;
  - the "from the internet" mark that opens macro workbooks safely.
- **Build and install.** Batch files, the Inno Setup installer and a Windows-only release job.

There is no Mac build today. Under the current rule, a Mac can therefore do only what any second machine may do: open the status pages, or connect remotely to the office PC.

Making it a real Mac app is moderate work. It is roughly 1,000 to 1,300 lines of product and build code, plus about as much test code. That is 5 SPEC-sized jobs if the Mac is a second, read-only desk, and 8 if it replaces the office PC. Four of those jobs change behaviour that a decision row protects, so Jason must rule on them. Separately, buying Apple's signing ($99 a year) decides whether the app opens cleanly and keeps its permission to read the Google Drive folder after each upgrade. Only Apple Silicon Macs running macOS 14 or later can run it: the pinned reader (`onnxruntime` 1.30.0) ships only `macosx_14_0_arm64` wheels.

## Build and operator side

**PyInstaller (`api_entry.spec`).**
- The spec is platform-neutral apart from `icon="app/assets/icon.ico"`. It needs an `.icns` (or Pillow conversion) and, on darwin, `target_arch="arm64"`, `codesign_identity` and `entitlements_file`.
- **universal2 is not possible:** `onnxruntime` 1.30.0 has only arm64 Mac wheels, and `opencv-python-headless` and `pypdfium2` ship separate arm64 and x86_64 wheels. Build arm64 only, with macOS 14 as the minimum.
- `freeze_support()` is already called in `api_entry.py`. PyInstaller's multiprocessing hook makes spawn work frozen on a Mac; the frozen smoke test must prove it.
- **The build lock cannot install on a Mac today.** PyInstaller requires `macholib; sys_platform == "darwin"`, and `requirements-build.lock` does not name it, so `--require-hashes` refuses the install (decision 191). Add it with `python tools/lockfiles.py hash`.
- The runtime lock already carries the macOS wheel hashes. It hashes every file PyPI publishes, and every pinned binary package has `macosx_*_arm64` wheels (checked: onnxruntime, opencv, numpy, shapely, pyclipper, pillow, pillow-heif, pypdfium2).

**Bundling, as `Build App.bat` does.**
- Use `electron-packager --platform=darwin --arch=arm64 --icon=assets/icon.icns`.
- Copy the onedir freeze into `Tax Document Console.app/Contents/Resources/tracker-api/` with `ditto` rather than robocopy. `process.resourcesPath` already points there.
- For notarization, every Mach-O in that folder (Python, the `.so` files, onnxruntime's dylib) must be signed with the hardened runtime and a timestamp. `@electron/osx-sign` walks `Resources`, but PyInstaller's `_internal` mix of code and data is the known fiddly part. Settle the entitlements by a signed test build.
- Package as a `.dmg` (hdiutil) with an "Applications" link. Prefer that to a `.pkg`: a pkg's postinstall runs as root, while the after-install step must run as the user. Decision 209 is still met because the app already runs the step at its first launch after the program changes.

**The batch files.**
- `Setup.bat` becomes `setup.command` or `setup.sh` (python3 ≥ 3.11 check, `python3 -m venv --clear .venv`, the two hash-checked installs, `npm ci`, `lockfiles.py stamp`, `python -m tracker.after_install --reason setup`).
- `Start App.bat` becomes `start.command` (`.venv/bin/python tools/lockfiles.py verify .venv`, then `node node_modules/electron/cli.js .`).
- `Build App.bat` becomes `build-mac.sh`.
- `Build GPU Pack.bat` and `pilot/Build Pilot Installer.bat` / `setup.iss` have no Mac counterpart.
- `npm` scripts would hide the Python half and the hash checks, so shell scripts match the existing pattern better. `tests/test_build.py` pins sentences between the batch files and the Python, so the same pins are needed for the scripts. The packaged app needs none of these.

**Signing (state this plainly to Jason).**
- An Apple Developer Program membership costs **US $99 a year**. It gives a Developer ID certificate, and notarization (`xcrun notarytool`) is included.
- **If the app is not signed:**
  - On Apple Silicon, code must still be ad-hoc signed to run at all. The packager does this.
  - A copy downloaded from a browser or GitHub's artifact page is quarantined. Since macOS 15, Gatekeeper blocks it with "Apple could not verify…" and offers no right-click Open. Someone must open System Settings → Privacy & Security → **Open Anyway** and enter an admin password, once per new version.
  - A copy carried on a USB stick (today's Windows route) is not quarantined and opens.
  - Either way, privacy grants are tied to the exact unsigned build, and macOS asks for them again after every upgrade. That includes permission to read the Google Drive folder, which the File Provider asks for (verify on the Mac). A launchd job cannot answer a prompt, so after an unsigned upgrade the scheduled pass fails until someone opens the app and grants access again.
- This is the Mac's version of P4, "unsigned, the SmartScreen warning is explained", and it is materially worse. For a Mac that runs the schedule, signing is close to required.

**`build.yml` and the cost rule.**
- A `macos-latest` (arm64) job is the Windows job's steps in bash: build, smoke the frozen API with no root, a dry pass over a scratch root, check that the package holds no store or settings, zip and hash. It also needs signing secrets and a `notarytool --wait`.
- Keep it tag-only like the Windows job (191, actions pinned by commit, 137 B3).
- At **10× Linux**, a 30 to 40 minute Mac release build (freeze, Electron download, notarization wait) costs about **300 to 400 Linux-minute equivalents per tag**. One Mac gate run of the suite (~15 min) costs about 150.
- Under decisions 207/211 the consistent rule is:
  - no macOS job on a push to `main`;
  - a `macos` label that works exactly like the `windows` label (one run when a draft is marked ready);
  - the Mac release package built and checked locally on the Mac with a check kit, as the Windows check is.
- Adding `macos-latest` to `ci.yml`'s Linux matrix would break the standing rule.

**A Mac check kit.**
- **Yes, if a Mac runs the app against the clients root.** `pilot/wintest/run_checks.ps1` is PowerShell bound to Windows paths. The Mac needs `pilot/mactest/run_checks.sh` (the same `-Tests` file list in parallel, then build the package) and a prompt.
- Hands-on steps that differ on a Mac:
  1. First launch through Gatekeeper ("Open Anyway"), or a clean open when signed.
  2. The Google Drive privacy prompt, then the same pass run by the launchd job with nobody at the Mac.
  3. The "Background Items Added" notice; switch it off and confirm that the next launch notices.
  4. The lock race (`python -m tracker.locking race`) on `~/Library/CloudStorage/...`, and L2 from §6.
  5. Sleep and wake around a scheduled time.
  6. The machine name staying stable across networks.
  7. Opening from the `.dmg` and from Downloads (translocation) is refused for scheduling.
  8. An accented file name written on the PC and moved on the Mac.
  9. Moving the app to the Bin and what remains (the agent file).
  10. Files that Drive has not downloaded yet ("Stream files"): a pass reads and files them, and the Overview's stat-only fingerprint does not download them.
- Steps that already passed on unchanged engine code are not repeated (Jason's 2026-09-29 preference).

**Runbook sections that are Windows-only.**
- §1: the data folder as `%LOCALAPPDATA%`, "Start the app from the Start menu", the `%LOCALAPPDATA%\Packages` refusal, the drive refusals (`subst`, VHD), Task Scheduler, the program in `%LOCALAPPDATA%\Programs`, and `Setup.bat` as a way to register the schedule again.
- §6 (moving machines): paths, `certutil -hashfile`, the GPU pack step, and `python -m tracker.checkpoint "%LOCALAPPDATA%\…" move-root`.
- Around the 2001–2133 lines, the package update and USB-stick steps.
- About 35 lines name `%LOCALAPPDATA%`, `Setup.bat`, `.exe`, Task Scheduler or `certutil`.
- A Mac needs a parallel set of paragraphs rather than edits, and `tests/test_single_source.py` must accept them. Decision 209's ban on "press this once after installing" wording applies to the Mac text too.

## The question Jason answers first

**Is the Mac a second machine in the same practice, sharing the clients root through Google Drive, or is it the office machine (replacing JPPC)?**

**If the Mac is a second machine**, the current rule (runbook §1, "One machine per clients root") is stricter than "app only, no schedule": the schedule, **Sort**, filing, **every save in the app** and **Roll Forward** happen on the designated machine only, and "any other machine may open a return's Status Report and read it; it does not run the app against the clients folder." The reason is that a lock file synced between two machines is not a lock (decisions 137 L6, 171). So:

- **Zero porting is needed** for what a second machine may do today. Open the status pages from the synced folder in Safari, or connect to JPPC with Microsoft's Windows App (Remote Desktop), as §1 already suggests.
- A real Mac app on a second desk would be a **read-only viewer**: the app with every writing command refused on any computer the designation file does not name. `vocab.writing_commands` already lists them. That relaxes, or more precisely makes enforceable, the one-machine rule, so it needs a decision row. It needs the homes, build and viewer jobs, but no launchd, memory-cap or durability work for passes.

**If the Mac is the office machine**, it takes the schedule through decision 209's existing move (`python -m tracker.after_install --move-schedule-here`). The PC removes its own task at its next start, which is cross-platform already. The firm carries `tracker.db` and `record-heads.db` over and runs `checkpoint move-root` to the Mac's CloudStorage path (records are keyed below the root, so this works). Every job below is needed, and signing becomes close to required, because the unattended pass must keep its permission to read the Google Drive folder.

Further questions, after that one:

1. **Signing.** Will the firm buy the Apple Developer membership ($99 a year)? If not, how does the app arrive (a USB stick avoids quarantine), and who re-grants the Drive permission after each upgrade?
2. **Protected View (190).** Accept the unmarked review copy on a Mac, or fail closed (no **Open** for macro workbooks, emails and zips on the Mac)?
3. **Room rule (131).** If the Mac writes, should returns be measured as if under the Windows root, so that Mac-made returns still open on Windows desks?
4. **Time Machine (186).** Should the data folder be excluded from Time Machine, matching "nobody backs up the data folder"?
5. **Hardware floor.** Apple Silicon and macOS 14 or later only. Is that acceptable? It is forced by the pinned reader.
6. **CoreML.** Is it worth a measured job, or is the CPU reader enough? Answer this after timing a season-sized pass on the Mac's CPU.
